# plugdata Patch Generator

You are generating Pure Data (`.pd`) patch files — plain-text files that define audio processing graphs. These files open in both plugdata and vanilla Pure Data.

## The .pd File Format

Every patch is a sequence of semicolon-terminated lines. The format is deliberately simple so it can be generated by hand or by code.

### Minimal Patch

```pd
#N canvas 0 0 450 300 12;
#X obj 100 50 osc~ 440;
#X obj 100 120 *~ 0.5;
#X obj 100 200 dac~;
#X connect 0 0 1 0;
#X connect 1 0 2 0;
#X connect 1 0 2 1;
```

This creates a 440Hz sine oscillator at half volume, output to both audio channels.

### Core Syntax

| Line Type | Format | Purpose |
|-----------|--------|---------|
| Canvas | `#N canvas X Y W H FONTSIZE;` | Define patch window (first line) |
| Object | `#X obj X Y TYPE ARGS;` | Place an object at (X,Y) |
| Message | `#X msg X Y CONTENT;` | Place a message box |
| Comment | `#X text X Y CONTENT;` | Place a text comment |
| Connect | `#X connect SRC SRC_OUTLET DST DST_INLET;` | Wire two objects together |
| Array | `#X array NAME SIZE float SAVE;` | Declare a named array |
| Array data | `#A 0 V0 V1 V2 ...;` | Array sample values |
| Subpatch start | `#N canvas 0 0 W H NAME 0;` | Begin nested subpatch |
| Subpatch end | `#X restore X Y pd NAME;` | End subpatch, place on parent |

### Object Indexing

Every `#X obj` and `#X msg` line gets a sequential 0-based index. `#X connect` lines reference these indices. `#X text` and `#X connect` lines do NOT get indices.

```
#X obj 50 30 osc~ 440;      // index 0
#X obj 50 80 *~ 0.5;        // index 1
#X obj 50 130 dac~;         // index 2
#X connect 0 0 1 0;         // osc~ out0 -> *~ in0
#X connect 1 0 2 0;         // *~ out0 -> dac~ in0
```

### Signal vs Control

Objects ending in `~` process audio-rate signals. Objects without `~` process control-rate messages (bang, float, symbol, list). You cannot directly connect signal outlets to control inlets or vice versa. Use `sig~` to convert control to signal, or `snapshot~` to convert signal to control.

## Patch Generation Workflow

When generating a patch, follow this process:

### 1. Understand the Goal

Determine what kind of audio processing the user wants:
- **Synthesizer** — oscillators + envelopes + filters + output
- **Effect processor** — audio input (adc~) -> processing -> output (dac~)
- **MIDI processor** — notein/ctlin -> logic -> noteout/ctlout
- **Utility/analysis** — measurement, conversion, routing
- **DAW plugin** — use param/playhead objects for host integration
- **Embedded (Daisy)** — restrict to hvcc-compatible objects only

### 2. Design the Signal Flow

Sketch the signal path from source to destination:
- What generates the sound? (oscillators, noise, samples, audio input)
- What transforms it? (filters, effects, envelopes, math)
- Where does it go? (dac~, send~, array, MIDI out)
- What controls it? (MIDI, GUI, parameters, logic)

### 3. Choose Objects

Read `references/objects.md` for the full object catalog. Key categories:

- **Oscillators**: `osc~`, `phasor~`, `noise~`, `saw~`, `tri~`, `pulse~`, `bl.saw~` (bandlimited)
- **Filters**: `lop~`, `hip~`, `bp~`, `vcf~`, `biquad~`, `svfilter~`
- **Effects**: `free.rev~`, `plate.rev~`, `chorus~`, `flanger~`, `phaser~`, `drive~`, `compress~`
- **Envelopes**: `line~`, `vline~`, `adsr~`, `envgen~`, `decay~`
- **Math**: `+~`, `*~`, `-~`, `/~`, `clip~`, `wrap~`, `expr~`
- **MIDI**: `notein`, `noteout`, `ctlin`, `ctlout`, `mtof`, `ftom`
- **I/O**: `adc~`, `dac~`, `notein`, `noteout`
- **Timing**: `metro`, `delay`, `pipe`, `tempo`
- **GUI**: `knob`, `nbx`, `tgl`, `bng`, `vsl`, `hsl`, `scope~`

For compilation targets (Daisy, DPF plugin), read `references/hvcc.md` — only a subset of vanilla objects + heavylib are supported.

### 4. Generate the .pd File

Use this template pattern:

```
Build an array of objects, each with {type, x, y, args}
Build an array of connections, each with {src, src_outlet, dst, dst_inlet}
Emit #N canvas header
Emit #X obj lines in order (track index)
Emit #X connect lines using tracked indices
```

### Positioning Guidelines

- Vertical flow: Y increments of 50-70 pixels per object
- Parallel paths: X offsets of 100-150 pixels
- Signal path goes top-to-bottom (source -> processing -> output)
- Control/modulation paths branch horizontally
- Start X at ~50-100, start Y at ~30-50

## Common Patch Patterns

### Monophonic Synthesizer

```pd
#N canvas 0 0 600 500 12;
#X obj 100 30 notein;
#X obj 100 80 mtof;
#X obj 100 130 osc~;
#X obj 250 30 notein;
#X obj 250 80 stripnote;
#X obj 250 130 adsr~ 200 50 0.7 300;
#X obj 100 200 *~;
#X obj 100 270 lop~ 2000;
#X obj 100 350 *~ 0.5;
#X obj 100 420 dac~;
#X connect 0 0 1 0;
#X connect 1 0 2 0;
#X connect 2 0 6 0;
#X connect 3 0 4 0;
#X connect 4 0 5 0;
#X connect 5 0 6 1;
#X connect 6 0 7 0;
#X connect 7 0 8 0;
#X connect 8 0 9 0;
#X connect 8 0 9 1;
```

### Audio Effect (DAW plugin)

```pd
#N canvas 0 0 600 400 12;
#X obj 100 50 adc~;
#X obj 100 120 lop~ 1000;
#X obj 100 190 *~ 0.8;
#X obj 100 260 dac~;
#X connect 0 0 1 0;
#X connect 1 0 2 0;
#X connect 2 0 3 0;
#X connect 2 0 3 1;
```

### Parameter with DAW Automation

```pd
#X obj 200 50 param cutoff 1000;
#X obj 200 100 sig~;
#X obj 100 150 lop~;
```

The `param` object exposes a "cutoff" parameter to the DAW's automation system.

### Subpatch (Abstraction)

```pd
#N canvas 0 0 300 200 mySubpatch 0;
#X obj 50 30 inlet~;
#X obj 50 100 *~ 0.5;
#X obj 50 170 outlet~;
#X connect 0 0 1 0;
#X connect 1 0 2 0;
#X restore 100 200 pd mySubpatch;
```

### Exposing Parameters for hvcc Compilation

```pd
#X obj 200 50 r gain @hv_param 0 1 0.5;
```

Format: `[r NAME @hv_param MIN MAX DEFAULT [TYPE]]`
Types: `float`, `bool`, `int`, `trig`, `dB`, `Hz`, `log`, `log_hz`

## Key Constraints

1. **Every line ends with `;`** — missing semicolons break the file
2. **Object indices are 0-based and sequential** — only `#X obj`, `#X msg`, `#X floatatom`, `#X symbolatom` count
3. **Signal/control boundary** — `~` objects only connect to `~` objects unless bridged
4. **No spaces in file paths** referenced by objects (soundfiler, readsf~, etc.)
5. **`[dac~]`** takes channel args: `[dac~ 1]` = left, `[dac~ 1 2]` = stereo, `[dac~ 1 2 3 4]` = quad
6. **`[adc~]`** similarly takes channel args for audio input
7. **hvcc compilation** only supports vanilla + heavylib objects (~323 total) — no ELSE, Gem, Cyclone, or pdlua
8. **Send/receive** (`s`/`r`, `send`/`receive`) provides wireless connections — useful for clean layouts and parameter distribution

## Reference Files

Read these when you need deeper detail:

- **`references/pd-format.md`** — Complete .pd syntax specification with all element types, subpatches, arrays, and GUI objects
- **`references/objects.md`** — Full object catalog organized by category (1,653 objects across 8 libraries)

- **`references/cyclone.md`** — Cyclone library reference (206 objects): Max/MSP compatibility layer, non-alphanumeric operators, `zl` modes, and vanilla Pd differences

- **`references/pd-lua.md`** — pd-lua API for writing custom Pd objects in Lua (inlets, outlets, DSP, GUI, clocks, arrays)

### Library Selection Guide

For **new patches**, prefer this order: ELSE > vanilla > Cyclone.
- **ELSE** — Active development, more features, better plugdata integration. Use for oscillators (`saw~`, `bl.saw~`), effects (`free.rev~`, `chorus~`), envelopes (`adsr~`), MIDI (`note.in`), GUI (`knob`, `scope~`)
- **Cyclone** — Use only when porting Max/MSP patches or when you need a specific Max object not available elsewhere
- **Vanilla** — Use for core objects (`osc~`, `*~`, `dac~`, `metro`, `send`/`receive`) and when targeting hvcc compilation

## When to Use pd-lua

If the user needs custom logic that doesn't exist as a built-in object, pd-lua lets you write objects in Lua:

```lua
local myobj = pd.Class:new():register("myobj")
function myobj:initialize(sel, atoms)
    self.inlets = 1
    self.outlets = 1
    return true
end
function myobj:in_1_float(x)
    self:outlet(1, "float", {x * 2})
end
```

Save as `myobj.pd_lua` in the patch directory, then use `[myobj]` in the patch. Read `references/pd-lua.md` for the full API.

## Checklist Before Writing a Patch

Before writing the .pd file, verify:

1. Does the signal path flow from source to output?
2. Are signal (`~`) and control domains properly separated?
3. Are object indices correct for all connections?
4. Is every line terminated with `;`?
5. Does the first line declare a canvas?
6. If targeting compilation, are all objects hvcc-compatible?
7. If it's a DAW plugin, does it use `adc~`/`dac~` (for effects) or MIDI objects (for instruments)?
8. Are positions reasonable for visual readability?

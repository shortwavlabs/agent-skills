# Accepted Constraints Ledger

Use for an existing-asset refinement. Keep entries brief; copy into the project's existing brief or review record rather than creating a parallel tracking system. Omit empty entries. An uncertain inference does not override an accepted choice. A later explicit user instruction can supersede one; record that change instead of silently rewriting history.

```text
SOURCE VERSION / BASELINE:
TARGET VERSION:
PASS OBJECTIVE:

AUTHORITATIVE USER FACTS
- Fact or latest direction — source/date:

LOCKED / ACCEPTED
- Accepted value or behavior — acceptance evidence:

PHOTO-INFERRED / UNCERTAIN
- Estimate — reference, uncertainty, and whether it may be revised:

ALLOWED TO CHANGE THIS PASS
- Parameter/part — permitted scope or range:

PROTECTED FROM REGRESSION
- Invariant — measurement or view that will verify it:

REFERENCE PRIORITY
- Reference → question it answers / variant / uncertainty:

BASELINE RENDERS
- Source, camera, settings, output and inspected feature:

CANDIDATE STUDIES (only for unresolved visible choices)
- A baseline / B restrained / C stronger; changed family and values:
- Selected candidate and reference evidence, or retain baseline:

NUMERIC VALIDATION
- Protected invariant, expected value/tolerance, measured result:

VISUAL QA
- Native hero crop, product/detail views and reference comparison:

FAIL CONDITIONS
- Specific regression that rejects this pass:

STOP RULE
- Defect resolved, protected systems pass, required outputs complete:

FINAL PASS/FAIL LEDGER
- Criterion — PASS / FAIL / NOT CHECKED / NOT APPLICABLE — evidence:

SUPERSEDED DECISIONS (only when needed)
- Previous constraint → replacement — user direction/source:
```

Before testing a candidate, confirm it changes only allowed entries. After inspection, record whether it was retained and which evidence supports acceptance. Carry the updated ledger into the next pass. Do not convert unsupported guesses into authoritative facts merely because they were saved in a previous version.
